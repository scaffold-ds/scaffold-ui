# Scaffold Color Methodology

## Purpose

This document defines the methodology used to create and validate Scaffold color palettes.

Scaffold uses **OKLCH** as the primary authoring representation and **sRGB** as the reference gamut for the core palette.

The goal is not to reproduce another design system. External generators and existing systems may be used as references, but Scaffold's final values are determined by this methodology.

## Palette Structure

Standard palettes use eleven steps:

```text
50
100
200
300
400
500
600
700
800
900
950
```

`500` is the primary family anchor.

## Palette Generation Pipeline

```text
                    500 Anchor
                        │
             ┌──────────┴──────────┐
             │                     │
        Light Curve            Dark Curve
             │                     │
         L / C / H             L / C / H
         nonlinear             nonlinear
             │                     │
            50                    950
             │                     │
             └──────────┬──────────┘
                        ↓
              Perceptual consistency
                        ↓
                sRGB gamut validation
                        ↓
             Cross-family balancing
                        ↓
                 Optical review
                        ↓
              Accessibility validation
                        ↓
                   Finalization
```

## 1. 500 Anchor

Each color family begins with a deliberate `500` anchor.

The anchor represents the intended identity and usable center of the family.

Different hues do not need identical lightness or chroma values.

## 2. Nonlinear L/C/H Curves

Lightness, chroma, and hue may all vary nonlinearly across the scale.

Do not assume that a palette should be generated by:

- keeping hue fixed
- linearly interpolating lightness
- uniformly scaling chroma

Hue shifts are allowed when they improve perceptual continuity, gamut behavior, or optical quality.

## 3. Perceptual Consistency

Evaluate the complete curve for:

- smooth lightness progression
- controlled chroma progression
- controlled hue movement
- absence of abrupt perceptual jumps
- coherent behavior on both sides of 500

## 4. sRGB Gamut Validation

Every final primitive color must be evaluated against the Scaffold sRGB reference gamut.

Out-of-gamut values must be corrected before locking.

Gamut correction should preserve the intended visual character as closely as practical.

## 5. Cross-Family Balancing

Evaluate every family alongside the others.

The objective is **not equal numeric chroma**. Different hues naturally occupy different regions of the sRGB gamut.

The objective is comparable perceived strength and a coherent visual hierarchy.

## 6. Optical Review

Mathematical correctness is not sufficient.

Review complete scales and compare them in actual UI contexts.

Check:

- perceived saturation
- perceived brightness
- transition smoothness
- relationship between families
- appearance at UI sizes
- appearance on light surfaces
- appearance on dark surfaces

## 7. Accessibility Validation

Validate the semantic combinations that components will actually use.

Examples include:

- text on surfaces
- icons on surfaces
- interactive controls
- focus indicators
- destructive states
- success states
- warning states

Not every shade needs to contrast with every other shade.

## 8. Finalization

A palette becomes canonical only after the complete validation pipeline passes.

Once finalized, palette changes are treated as design-system token changes and should be reviewed accordingly.

## External References

Tools such as Tints.dev and existing systems such as Tailwind may be used for:

- initial palette exploration
- curve comparison
- discovering L/C/H relationships
- visual reference

They are not authoritative sources for Scaffold's final values.
